Build the application front to back, in the order a user meets it. Every day ends with something you can click in the browser and check for yourself — no development scripts, no direct database access.

Planning rule: every day ends with one screen you can open in a browser and one click-through that proves it works. Server work does not get its own days — it arrives as the thinnest cut that lights up the day's screen.

What this replaces: the previous risk-ordered breakdown, which front-loaded unknowns and deferred the browser to the last two slices. Caido access and quota recovery have since been verified as reachable, which removes the reason to lead with them.

Already standing

What the first screen is built on.

Banked during Sprints 01–02 and the §22 milestone. Stated here so it is not re-planned: it is what these days draw on, not work still to do.

Phase A / Days 1–3

Getting in.

Before any target is open. The front door, the list of targets, and the way a new one comes into being.

Recommended first commitment
DAY 01Connect

Authenticate against the server

Launching the app lands on a connection screen: server URL and password. Nothing else is reachable until it passes.

Connect form · wrong-password state · server-unreachable state · reconnect banner

Test byA wrong password is refused with a reason and issues no session. The right one lands on the welcome screen. Reload — still in. Clear the session — back at Connect.

Server slice: a session route on the existing single listener, password verified server-side, token issued. Health stays unauthenticated and keeps saying one word.

DAY 02Welcome

See every target you hunt

A left rail of target folders, recent hunts beside it, and a search box. The shape OpenCode uses for projects, holding targets.

Welcome screen · target rail · recent-hunt list · empty state

Test byTwo registered targets both appear with their folder paths and last activity. A target whose folder has gone missing shows as unavailable rather than vanishing. Search filters the rail.

Server slice: read the target registry out of control.sqlite. No writes this day.

DAY 03New target

Create a target from a folder

Pick a path, name the target, set its scope. The folder becomes a hunt: its own database, migrated on creation.

Open-folder dialog · new-target form · migration-failed state

Test byCreate a target against a folder; it appears at once. Restart the server — still there, with migration rows in its hunt.sqlite. Creating a second target does not touch the first file.

Server slice: registry insert plus a per-target migrator run. Settle the partial-fleet-migration policy here — a target that fails to migrate is marked unavailable and the rest keep serving.

Boundary: the folder picker runs server-side. The browser never reads the filesystem.

Phase B / Days 4–8

The hunt.

Opening a target drops you into the hunt interface. By the end of this phase you can run an investigation from the browser and read what it did.

DAY 04Hunt shell

Open a target

The hunt view, empty. Target header, scope, counts, an inert compose box. The frame everything else hangs on.

Hunt shell · target header · empty transcript

Test byOpen each of two targets in turn. The header shows the right name, scope and counts, and no data from the other target appears anywhere. A deep link to a target URL opens straight there.

Server slice: open the per-target store on demand, one read-only summary query. Prove the no-cross-target-read path through the UI rather than through a test.

DAY 05Compose

Start a run from the browser

Type an instruction, pick a model, press start. The compose box stops being inert.

Compose box · model picker · running state · stop control

Test byAim an instruction at the rate-limit fixture and start it. OpenCode launches, an attempt row is created, and the fixture receives traffic. Stop ends it, and the attempt settles honestly rather than hanging.

Server slice: an HTTP route onto the existing harness launch and attempt creation. Credentials are minted per attempt exactly as they are today.

Boundary: from this day the agent executes real actions on your machine. Only the existing fail-closed policy hook constrains it, and the perimeter day is Day 21. Twelve days of fixture-only work sit in between — that is the cost of building front to back, and it is accepted deliberately.

DAY 06Transcript

Watch it work

Turns, tool calls and recorded results appear as they happen, in the order the store assigned them.

Live transcript · tool-call item · denied-action item · recorded-observation item

Test byStart a run and watch. Each tool call shows its arguments and result; a denied action reads as denied; a recorded observation reads as recorded. Nothing appears twice.

Server slice: the thinnest cut of the event consumer — ordered reads behind a durable cursor, pushed to the browser.

DAY 07Reconnect

Survive a reload mid-hunt

The browser is not the source of truth, and this is the day that stops being a claim.

Reconnecting banner · catch-up state · reconciled-attempt notice

Test byStart a long run, reload the browser halfway. The transcript reconstructs to the same point and carries on. Kill the server, restart it, reopen: every committed turn is there and the unsettled attempt is reconciled rather than silently dropped.

Server slice: cursor catch-up on connect, advisory wake-ups, startup reconciliation surfaced to the client.

DAY 08Sessions

Read past hunts and the briefing

The session list for this target, and the panel showing exactly what a fresh session is told before it starts.

Session list grouped by day · session search · briefing panel

Test byOpen a finished hunt and read it end to end. Open the briefing on a fresh session: it names what is known, what is still untested, and a next action that follows from recorded observations rather than from the prompt.

Server slice: the briefing already exists and is already tested. This day renders it and adds the session query.

Checkpoint A

You can start, watch, interrupt and re-read an investigation entirely in the browser.

If this loop is awkward to use, fix it here. Everything after this phase assumes it is pleasant.
Phase C / Days 9–13

What it learned.

The knowledge graph, made visible. Observations, findings, assets, and the frontier of what has not been tried.

DAY 09Observations

Every result, including the dull ones

A negative result is as valuable as a positive one, and the list treats it that way.

Observation list · dimension chips · observation detail

Test byEvery observation from a completed hunt is listed in sequence order with its dimensions. A negative result is as visible as a positive one. Each row traces back to the attempt that recorded it.

Server slice: a paged read over the append-only table. No write path exists and none is added.

DAY 10Findings

The list that matters

Severity, status, confidence, and which target. The screen you open when someone asks what you found.

Finding list · severity and status filters · empty state

Test byFindings from a completed hunt appear with severity and status. Filtering by status narrows the list and survives a reload. A target with no findings says so plainly.

Server slice: the finding record and its read path. First new domain table since Sprint 02.

DAY 11Finding detail

Why you believe it

The claim, the observations underneath it, its limitations, and what changed between revisions.

Finding detail · supporting observations · limitations · revision drawer · conflict dialog

Test byOpen a finding and trace it to the observations that support it. Edit it and the revision appears in the drawer. Submit a conflicting update and it is refused with a reason, leaving the stored finding untouched.

Server slice: whole-finding revisions with conflict rejection. New limitations cannot be silently overwritten.

DAY 12Assets

What exists, and what you tested on it

Hosts, endpoints and parameters discovered so far, each showing its own testing history.

Asset list · asset detail · coverage column

Test byRun a hunt twice over the same endpoint. One row, not two. Each asset shows what has been tested on it and what has not.

Server slice: surface the type-specific identity rules. Endpoint identity is where over-normalisation bites first — URL plus method, against URL plus method plus role — and this screen is where a wrong choice becomes obvious.

DAY 13Frontier

What it has not tried yet

Untested dimensions, each appearing once, each saying why it is still open.

Frontier list · disposition reason · planner budget indicator

Test byAfter a bounded hunt, each untested dimension appears exactly once with a reason you can read. The planner's disposition stays inside its budget rather than enumerating the whole space.

Server slice: largely banked — untested dimensions already render once in the briefing's volatile tail. This day gives them a screen.

Checkpoint B

Everything the agent learns is visible, traceable to its source, and honest about what it has not covered.

A useful workbench for manually driven hunts, well before autonomous operation is ready.
Phase D / Days 14–16

Evidence.

Caido runs locally with a GraphQL API that already exposes requests, responses, findings and scope. This is a fetch, a hash and a write — not a spike.

DAY 14Traffic

See the target's traffic

Flows pulled from Caido for this target, filterable by host, status and method.

Traffic list · host/status/method filters · Caido-unavailable state

Test byWith Caido running, flows for the target list and page correctly. Stop Caido: the screen says the source is unavailable rather than showing an empty list that looks like no traffic.

Server slice: a GraphQL client against the local Caido instance, reading its bearer token at runtime. Paging over requestsByOffset.

Boundary: confirm Caido's licence permits programmatic access before this ships. It is a legal check, not a technical unknown, and it does not gate the build.

DAY 15Flow detail

Capture a flow as evidence

Read the raw exchange, then take a copy that no longer depends on Caido keeping it.

Flow detail · raw request/response panes · capture control · capture-failed state

Test byOpen a flow, read the raw request and response, press capture. The artefact is stored content-hashed outside SQLite and linked to the target. Capturing the same flow twice stores it once.

Server slice: evidence write with content hashing. Evidence stays out of the database, as the architecture requires.

DAY 16Evidence locker

Evidence that outlives its source

The whole point of capturing rather than linking.

Evidence list · artefact viewer · incomplete-capture state

Test byCapture evidence, then delete the Caido project it came from. The artefact is still readable. Interrupt a capture mid-write: it stays visibly incomplete rather than presenting as whole.

Server slice: integrity verification on read, and an explicit partial state. A half-written artefact that looks finished is worse than none.

Keep it small: referenced-flow ingestion, not a traffic browser. Caido remains the place you explore traffic; this is the place you preserve the parts that matter.

Phase E / Days 17–18

Output.

The thing you actually hand over, and the honesty mechanism that keeps it from lying as the investigation moves on.

DAY 17Report

Generate a report you could send

Built from a frozen snapshot of a finding and its evidence, so it says the same thing tomorrow.

Report generation · report view · export

Test byGenerate a report from a finding. It renders the claim, the supporting observations and the attached evidence as they stood at generation time, and exports to a file you can open outside the app.

Server slice: snapshot the finding and evidence set, then render from the snapshot — never from live state.

DAY 18Freshness

A report knows when it went stale

The investigation keeps moving. The report should admit when it has been left behind.

Stale badge on report · report version list · regenerate flow

Test byChange a finding in a way that qualifies. The existing report is marked stale in place, still readable, not overwritten. Regenerating produces a new version alongside the old one.

Server slice: a qualifying revision marks dependent reports stale. Versioned report text, not dependency propagation across the graph.

Checkpoint C

A hunt now produces something you could hand to someone else, with evidence behind it and a visible shelf life.

Everything after this makes the tool run unattended. Nothing after this is needed to get value from it.
Phase F / Days 19–23

Keeping it running.

Unattended operation, made inspectable. Who is working, what is stuck, where the agent may go, and what happens when capacity runs out.

DAY 19Workers

Two workers, visible lanes

Who is working on what, right now, and a stop button that actually stops.

Worker lanes · claim indicator · stop control · concurrency setting

Test byRun two attempts. The lanes show who holds which intent, and neither can claim the other's. Stop one: it settles and can no longer make authoritative changes. The other is unaffected.

Server slice: persisted claiming, attempt-local workspaces, a concurrency limit. Attempt authority and the write fence already enforce the stopping half.

DAY 20Blockers

Why nothing is happening

The screen you open when the app is quiet and you cannot tell whether that is good news.

Blocker list · blocker detail · resolve action

Test byInduce a blocker — a policy denial, a missing credential — and it appears with a reason specific enough to act on. Resolve it and the work continues without a restart.

Server slice: a blocker projection over existing state. No new truth, just a question the store cannot currently answer quickly.

DAY 21Perimeter

Constrain where the agent may go

Sixteen days after the agent began executing real actions. The one genuinely unproven item on this roadmap.

Supported-paths panel · perimeter violation state · policy-change notice

Test byFixture tests cover redirects, subprocesses and a policy change taking effect mid-run. The screen states plainly which execution paths are constrained and which are not.

Server slice: constrain the selected execution path beyond its initial tool arguments. Which paths those are follows from what Days 5–8 actually built.

Boundary: a universal sandbox is not reachable in a day, and may not be reachable at all. If it is not, ship a constrained supported path at ScopeWeaver's level of strictness and say so on the screen. An honest limit is worth more than a claimed perimeter.

DAY 22Quota

Wait out a usage limit and resume

Capacity runs out at 2am. The hunt should pick itself back up without you.

Usage windows per provider · reset countdown · resume-when-reset toggle · snooze

Test byWith a recorded quota fixture, the run fails as a usage limit carrying a reset time, and the screen shows the window. Enable resume-when-reset, restart the server, and the continuation still fires after the reset — with no timer to restore.

Server slice: persist the recovery decision rather than a timer; derive due work from an indexed query on a shared slow tick; make command ids deterministic so replays dedupe; re-validate everything at fire time. The sweep is a read plus a dispatch, so it never holds the write lock while waiting.

Boundary: wait-and-resume only. Switching to another model on exhaustion has no reference implementation anywhere we can draw on, and sits in the backlog below. Use recorded fixtures; do not exhaust a real subscription to test this.

DAY 23Policy

See what is allowed and what was refused

The fail-closed hook already decides. This is the day you can finally read its decisions.

Policy rules · decision log · pending approvals · policy-outage state

Test byA denied action from a real run appears in the log with its reason. Take the policy service down: the screen shows an outage and actions are denied — never silently permitted.

Server slice: the decision path exists and is tested. This renders it and records decisions for later reading.

Phase G / Days 24–26

System.

Settings-shaped screens. Each is small, and each one removes a reason to open a terminal.

DAY 24Harnesses & tools

Models, harnesses and MCP servers

What the agent can run on, and what it can reach.

Harness status · model eligibility · MCP server list with health and exposed tools

Test byConnected MCP servers list with their tools. Stop one: it shows unhealthy within a tick rather than staying green. Marking a model ineligible keeps the next run off it.

Server slice: read-only status, plus the eligibility flag the quota day already needs.

DAY 25Notifications

Route findings to Discord

The first thing that leaves the machine, driven off the outbox written since Sprint 02.

Channel routing · delivery log · failed-delivery state

Test byRoute a significant finding to a channel; it arrives, identifies its source event and links back to the app. Break the network mid-send: the outbox keeps it and it delivers after restart, with the failure visible meanwhile.

Server slice: outbox dispatch with leases and retry scheduling, and a Discord sink. The outbox is a queue of side-effect requests; it does not promise exactly-once remote delivery, and the screen should not imply it does.

DAY 26Event log

The raw stream, and settings

The last screen that removes a reason to open the database by hand.

Event log in sequence order · event detail · settings form

Test byThe append-only event stream for a target reads back in sequence order. An event carrying an undeclared field renders rather than breaking the page. Settings survive a restart.

Server slice: a paged event read, and the reader rule that tolerates undeclared fields by returning nothing rather than throwing.

Checkpoint D

A usable personal tool: hunts you start and watch, knowledge you can trace, evidence that outlives its source, reports that admit when they are stale, unattended operation you can inspect, and Discord when something matters.

Expand in response to actual use, not in anticipation of it.

Start at the front door.

Day one is a password field. It is not glamorous, and it is the first thing that makes the work real: from here on, every evening ends with a screen you can open and a thing you can click, and progress stops being a claim about test coverage.

The rate-limit fixture stays the proving ground. A bounded result, a fresh session, a better next question — now visible in a browser rather than inferred from a log.
